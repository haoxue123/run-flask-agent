## 一、根本目标与假设

### 1.1 它要解决的根本问题

项目自己给出的定义（`ARCHITECTURE.md` 第 13 行、`docs/interview-narrative.md` 第 1 节）：

> 把"真实跑步数据"转化为"科学、安全、循序渐进的训练计划"，并随执行情况自我审查、动态调整。

面试叙事里把定位收得更窄也更锋利——**不做静态计划生成器，做「计划 → 执行 → 复盘 → 调整」的自适应教练闭环**。

这个定位是清晰的，而且是有差异化的：竞品（running_page 等）普遍停在可视化或一次性生成。

### 1.2 成立所需的前提假设，以及验证情况

闭环要成立，必须同时满足 5 个假设。**只有 2 个被验证。**

| # | 假设 | 验证方式 | 结论 |
|---|------|----------|------|
| H1 | 用户能拿出可解析的真实运动数据 | 实测 `get_all_runs()` | ✅ 通过（40 条记录，3 个文件） |
| H2 | LLM 能稳定产出结构化计划 | `response_format=json_object` + 正则兜底 | ✅ 通过（架构上有双保险） |
| H3 | RAG 能提供可靠知识 | 实测检索"马拉松比赛如何补水" | ✅ 通过（SiliconFlow bge-m3，命中 3 条且相关） |
| H4 | **确定性科学内核能保证安全** | 实测 `calc_training_summary` | ❌ **失败**，指标静默归零（见 3.3） |
| H5 | **闭环的"测量"环节能量化偏差** | 实测 `build_review_report()` | ❌ **失败**，输出错误结论（见 3.1） |

**最关键的一句话**：H4 和 H5 恰好是项目差异化价值所在，也是两个唯一没被验证的假设。

## 三、在进展评估

### 3.1 【P0】周复盘：测量环节在时间窗口上设计错了

这是本次审查最严重的问题，因为它击穿的正是核心卖点。

**实测结果**（真实数据，40 条记录）：

```
has_plan: True | has_actuals: True
完成度: planned 12.8km / actual 0km，完成度 0%，缺 4 个跑步日
负荷: acute_trimp=0.0, chronic_trimp=0.0, acwr=None, has_hr_data=False

→ 报告结论：「下周调整建议：跑量减量、强度降强度、恢复增加恢复日」
```

但事实是：**数据里有 40 条真实跑步记录，且 40 条全部带心率。**

**根因链**：

1. `load_actuals()` → `get_all_runs()` 拿到 40 条 ✅（这一步是对的）
2. `compute_compliance()` 用 `in_window(a)` 过滤「近 7 天」（`weekly_review.py:134`）
3. `compute_load()` 同样用 7 天 / 28 天窗口（`:168-169`）
4. `calc_training_summary()` 用 `today = datetime.now().date()` 过滤（`training_science.py:237`）
5. 数据最新日期 2026-07-18，今天 2026-08-29 → **全部落在窗口外**
6. `actual_volume = 0`、`has_hr_data = False`

**为什么这比报错更危险**：`has_actuals=True`（列表非空），所以不会走"没有数据"的提示分支，而是**静默给出错误结论**。报告甚至说"暂无带心率的执行数据"——真实原因不是没心率，是数据不在时间窗口内，提示语是误导性的。

**正确的设计**：复盘窗口应锚定在**计划周期**上（`plan.json` 的 `generated_at` + `plan_duration`），而不是"相对今天的 7 天"。否则两个场景必然出错：
- 用历史数据演示 → 永远显示完成度 0%
- 真实用户 3 天没跑 → 显示 0%，忽略他上周的正常训练

### 3.2 【P0】VDOT 配速：与项目自己的知识库互相矛盾

**代码输出**（`vdot.py`，VDOT 51.9，即 10km/40min）：

| 区 | `vdot.py` 算出 | 项目知识库 `ref_numeric_tables.md` 插值 | 偏差 |
|---|---|---|---|
| E | 6'47" ~ 5'24" | ~4'56" | 快端 **+28 秒/km** |
| M | 5'00" | ~4'12" | **+48 秒/km** |
| T | 4'33" | ~3'42" | **+51 秒/km** |
| I | 4'00" | ~3'17" | **+43 秒/km** |

（知识库表原文标注"Daniels 简化版"：VDOT 50 → E 5:05 / M 4:20 / T 3:50 / I 3:25；VDOT 55 → E 4:40 / M 3:58 / T 3:28 / I 3:05。）

**同一个项目里，知识库查表和代码内核给出了两套差 30–50 秒/km 的配速，且都声称来自 Daniels。** 两者都会被注入给 LLM（知识库经 RAG 检索，VDOT 锚点经 `build_vdot_anchor`），模型会收到互相打架的指令。

**方法层面的问题**：`vdot_training_paces()` 把「该 VDOT 在 10km 上的比赛配速」当作 100% VO2max 锚点，再用 `配速 = 锚点 / 百分比` 推导各区。这个做法有两个可疑点：
1. 10km 比赛配速在 Daniels 体系中不等于 I 区（100% VO2max）配速——I 区配速应更快；
2. 用除法换算配速，隐含假设 VO2 与速度成正比（过原点直线），但真实关系存在非零截距。锚点一旦偏低，除法会把误差在低强度区放大——这与实测"强度越低偏差越大"一致。

**文档的断言与代码不符**：`docs/interview-narrative.md` 第 3.1 节写「验证：10km/40min → VDOT 51.9，各区间配速与 Daniels 公开对照表吻合」。但 `vdot.py` 的自测（`:200-211`）只断言了 VDOT 值域和**区间内部顺序**（`I < T < E[0]`），**从未验证过配速的绝对值**。测试全绿，但绿的是错误的断言。

### 3.3 【P1】教练上下文仍被截断到 5 条

`get_all_runs()` 去掉 `limit=5` 的修复**只应用到了周复盘路径**。`data_tool.py:331` 仍然是：

```python
recent_runs = get_recent_runs(limit=5, data_dir=data_dir, files=activity_files)
```

实测对比：

| 指标 | `get_all_runs()` | `build_runner_profile()` |
|---|---|---|
| 记录条数 | **40** | **5** |
| 日期跨度 | 2026-01-20 ~ 2026-07-18 | 2026-06-10 ~ 2026-07-18 |

后果：教练对话里注入的"训练科学指标"（负荷/ACWR/就绪度）基于 5 条记录计算。而 ACWR 的分母需要 28 天慢性负荷——5 条记录根本填不满窗口。

`docs/interview-narrative.md` 第 4 节写「实测从 5 条 → 40 条」，给人的印象是已修复，**实际只修了一半**。

### 3.4 【P1】负荷指标静默归零：缺数据表现为"安全"

`calc_training_summary()` 在数据落在窗口外时返回：

```
weekly_trimp=0, training_load=0, acwr=None, readiness=70
```

问题不在返回 0，而在 **`readiness=70` 是一个"看起来正常"的默认值，`acwr=None` 会让 `derive_adjustments()` 跳过全部负荷判断**（`weekly_review.py:221`）。结果是：没有数据 → 系统判定"安全" → 安全检查被静默跳过。

对"运动安全"这种场景，缺数据必须显式表达为 **Unknown**，而不是落入安全档。

## 五、优先级建议

排序原则：**先修"会让面试讲不下去"的，再修"会让你丢数据的"，最后才是打磨。**

1. **修周复盘窗口**：把 `compute_compliance` / `compute_load` 的窗口从"相对今天的 7 天"改为"锚定计划周期"（`plan.json` 的 `generated_at` + `plan_duration`）。修完立刻用现有 40 条数据重跑，确认完成度不再是 0%。

## 六、一句话总结

**项目的架构设计和定位判断是对的——「自适应闭环」这个差异化选择站得住；但闭环的"测量"环节在时间窗口上设计错了，导致核心卖点在实际数据上输出的是错误结论，而且错得很安静。修好 P0 的两项（复盘窗口、VDOT 配速），这个项目的故事才真正讲得圆。**
