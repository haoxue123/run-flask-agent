# 马拉松训练计划 Agent · 面试叙事与架构说明

> 用途：作为简历作品 / 产品经理 / 技术面试的"讲清楚"底稿。
> 一句话定位：**一个会"看执行、动态调计划"的自适应跑步教练，而不是一张静态计划生成器。**

---

## 1. 为什么做这个东西（问题定义）

跑者最大的痛点不是"没有计划"，而是**计划赶不上现实**：加班、伤痛、天气、状态波动，
让原定课表失真。市面上的工具（含 GitHub 上多数开源 demo）只做"生成计划"，
少数做了数据可视化（如 running_page，4.4k★，但它是个人跑步主页，不是教练）。
**"计划 → 执行 → 复盘 → 调整"的闭环，在开源社区普遍没做好**——这正是本项目的差异化定位。

我的第一性原理判断：一个教练型 Agent 的真正价值，
= 现实偏离计划时**动态适配**的能力，而不是出一张漂亮的静态表。
所以我把工程重心放在"闭环"和"科学内核"上，而非堆 UI。

---

## 2. 整体架构（技术栈）

| 层 | 技术 | 作用 |
|---|---|---|
| Web 服务 | Flask（单进程，gunicorn 可部署） | 提供教练对话、数据上传、周复盘接口 |
| 大模型 | DeepSeek 双模型（生成 + 反思） | 自然语言交互、计划生成、对话 |
| 知识库 | ChromaDB + SiliconFlow BAAI/bge-m3 嵌入 | RAG 检索跑步科学知识 |
| **科学内核** | `physiology.py` / `training_science.py` / `vdot.py`（纯标准库、确定性） | 配速、负荷、VDOT 等**全部数字由公式算出**，不靠 LLM 编 |
| 长期记忆 | mem0（DeepSeek 抽取 + ChromaDB 存储） | 跨会话记住用户事实/偏好 |
| 数据接入 | `data_tool.py`（GPX/TCX/FIT/CSV 解析 + 手动录入） | 把真实运动数据取回喂给科学内核 |

**关键设计取舍**：科学内核与 LLM 解耦。
LLM 负责"理解和表达"，确定性内核负责"计算和决策"。
这样配速、负荷、调整建议都可单测、可审计、可解释——面试时能直接说
"这不是黑盒，每一句建议背后都有公式和规则"。

## 3. 科学链路（面试最该讲透的部分）

### 3.1 VDOT 全链路（本次补全）
`比赛成绩 → VDOT → 全强度区配速`

- 输入：用户填"近期比赛：距离 + 时间"（如 10km / 40min）。
- `vdot_from_race()`：用 Jack Daniels《Running Formula》的 VO2max 预测方程
  （Daniels & Ruby 速度法）由比赛成绩算出 VDOT≈52。
- `vdot_training_paces()`：按 Daniels 各强度区占 VO2max 速度的百分比
  （E 59–74% / M 80% / T 88% / I 100% / R 106%）推导 E/M/T/I/R 配速。
- 结果直接注入教练对话上下文，教练据此给配速建议。

> 验证：10km/40min → VDOT 51.9，各区间配速与 Daniels 公开对照表吻合。
> 公式来源是事实（非推测），数值可对表验证。

### 3.2 周复盘闭环（核心价值）
`计划 vs 实际 → 量化偏差 → 推导调整`

1. **测量**：`load_actuals()` 汇聚三源实际数据——
   计划按天记录、上传文件解析、手动录入（本次已修复"手动录入覆盖历史"的 bug）。
2. **决策**（确定性规则，可解释）：
   - ACWR（急性/慢性负荷比）> 1.5 → 强制减量 + 降强度 + 加恢复（防伤）；
   - 计划完成度 < 60% → 减量；≥ 90% 且负荷安全 → 增量；
   - 有伤病史 → 保守处理。
3. **输出**：自然语言复盘报告 + 下周调整建议 + 依据。
   教练对话说"帮我复盘本周"即触发；`GET /api/coach/weekly-review` 返回 JSON。

### 3.3 为什么用确定性内核而不是全靠 LLM
- 可复现：同样输入永远同样输出，便于测试和排错。
- 可解释：每句建议能回溯到具体公式/规则，对"运动安全"这种高风险场景尤其重要。
- 成本与延迟：常规计算走本地纯函数，不烧 token。
- LLM 只在"表达与理解"上发力，不碰"数字真伪"。

## 4. 数据接入（本次提升为"一等公民"）

- 修复：手动录入从"覆盖历史"改为**追加**，多次记录不再丢失。
- 修复：`get_all_runs()` 去掉原本 `limit=5` 的截断与文件缓存依赖，
  周复盘现在能读到窗口内**全部**真实执行数据（实测从 5 条 → 40 条）。
- 可见性：新增 `GET /api/data/actuals` 直接返回"喂给闭环的实际数据"及其来源统计；
  `/api/data/refresh` 上传后返回解析摘要（摄入几条、哪些日期）。
- 降级：Garmin 自动同步当前不可用（OAuth 限制），但手动上传 + 手动录入已能完整驱动闭环。

---

## 5. 面试可讲的"项目亮点"清单

1. **闭环思维**：不是生成器，是自适应教练（计划→执行→复盘→调整）。
2. **确定性内核 vs LLM 解耦**：科学可审计，安全可解释。
3. **VDOT 全链路**：把"比赛成绩"变成"全部训练配速"，有真实公式背书。
4. **工程完整度**：Web + RAG + 双模型 + 长期记忆 + 可单测内核，能跑能演示。
5. **务实降级**：自动同步挂了，手动链路照样闭环——知道什么该自研、什么该降级。
6. **可验证**：pytest 覆盖科学内核与数据接入（本次 + 此前共 20+ 用例全绿）。

---

## 6. 演示路径（30 秒讲清楚）

1. 打开 http://127.0.0.1:5000 → 数据页上传一个 GPX/TCX/CSV（或填手动跑步）。
2. 在教练对话说"帮我复盘本周" → 看到计划 vs 实际、负荷、下周调整建议。
3. 在数据页填"近期比赛成绩" → `/api/data/vdot` 返回 VDOT 与 E/M/T/I/R 配速表，
   教练此后据此给配速建议。

> 注：部署见 `deploy/`（Docker Compose / Railway 两套方案），国内访问优先方案 A。
